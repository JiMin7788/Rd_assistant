`docs/03_RECORDER_SPEC.md`를 대체하지 않고 **덧붙인다**. 충돌 시 이 문서가 우선.

## A1 — 콘텐츠 영역 정의에 `chrome` 추가

### 문제

명세 §4.3은 콘텐츠 영역을 "client − 우측 사이드바"로 정의했다. 실제 LDPlayer 14는
**상단에도 탭바를 그린다.** 실측 프레임(1499×2108) 픽셀 분석 결과:

```
y=  0        (73,73,73)   창 테두리 1px
y=  2..39    (36,36,47)   LDPlayer 타이틀바 + 탭바   ← 콘텐츠에 포함돼 있었음
y= 40        (39,54,123)  게임 시작
x=  0        (31,31,41)   좌측 테두리 1px
x=1459..1498 (31,31,41)   우측 아이콘 사이드바 40px  ← 유일하게 제외되던 부분
```

상단 40px가 콘텐츠에 포함된 상태에서 `(u,v)`는 게임이 아니라 **에뮬레이터 창** 기준
좌표다. 원점이 40px 밀리고 세로 스케일이 2108/2068 = 1.019배 어긋난다. 데이터가
자기모순은 아니어서(같은 세션 안에서는 일관됨) 어떤 검증에도 걸리지 않는다.

### 변경

- `Viewport`의 `sidebar_right_px: int` → **`chrome: Insets`** (4면 전부)
- `content = client − chrome − letterbox`, `inner = client − chrome` (레터박스 검출 대상)
- `chrome`은 **자동 검출하지 않고 config에 고정**한다. 검정이 아니라 레터박스 스캔이 못 찾는다
- `[target.chrome]` 테이블 신설. `env_fingerprint`에 포함 → 값이 바뀌면 이전 세션과 섞이지 않는다
- 측정 도구 `tools/verify/g2b_chrome.py` 추가 (§G2b)

### 검출 보조 (`rdom.recorder.probe`)

`suggest_chrome()`은 **제안일 뿐**이다. 각 가장자리마다 "가장자리 대표색과 일치하는
마지막 지점"을 찾고, 그 직후가 **명확한 색 단차**일 때만 값을 낸다. 아니면 0(경계 못 찾음).

- 균일 구간 길이로 찾으면 탭바 중간의 글자·아이콘에서 끊겨 top을 심하게 과소평가한다
- 최대 색 단차로 찾으면 게임 아트의 그라디언트를 잡는다 (실측에서 left=148, right=188이 나왔다)
- 실제 프레임 검증: `{'left': 2, 'top': 40, 'right': 40, 'bottom': 0}` — 수동 실측 `{1, 40, 40, 0}`과 일치
- **0이 나오면 사람이 프로파일을 읽는다.** 틀리는 방향은 이쪽이어야 한다

## A2 — 출력 해상도를 캡처 종횡비에서 유도

### 문제

`[capture] out_res = [720, 1280]`가 소스와 무관하게 강제됐다.

```
소스 1499×2108 (0.711)  →  출력 720×1280 (0.5625)
가로가 21% 눌린 영상이 43분간 1.24GB 기록됐고 경고는 없었다
```

우연히 LDPlayer의 가로 스트레치와 대략 상쇄됐지만, 창 크기가 바뀌면 바로 깨진다.

### 변경

- `out_res` → **`out_long_edge`** (기본 1280). 짧은 변은 `plan_out_res()`가 소스 종횡비에서 계산, 양변 짝수(yuv420p 요구)
- **캡처 영역을 client가 아니라 `content`로** 바꾼다. 영상에 에뮬 크롬이 아예 들어오지 않고, `(u,v)`가 영상 픽셀에 선형으로 대응한다
- `session.json`에 `capture.covers = "content"`, `env.content_res` 기록. `schema_version` 1 → 2
- 이전 스키마 세션은 R8 도구가 **거부**한다 (좌표가 영상에 대응하지 않으므로)

## A3 — 이벤트 시각 단조성 검사 분리

`action`은 누를 때 시각을 갖지만 뗄 때 기록되므로 **파일 순서상 항상 역전**이다
(spec §3.2 의도대로). 최초 구현의 `verify_events`가 이걸 위반으로 잡아 첫 세션이
`CORRUPT`로 기록됐다.

- `time_monotonic` — `action`을 제외한 원시 이벤트만 검사
- `action_time_monotonic` — `action`끼리 비교 (신설). 제외만 하면 액션 순서가 아예 검사되지 않는다

## A4 — R8 위치 변경

명세 §9는 `tools/replay_overlay.py`라고 썼으나, 테스트에서 import 해야 해서
**`src/rdom/tools/replay_overlay.py`** (entry point `rdom-replay`)로 옮겼다.

구현 메모:

- 마커는 ffmpeg `drawbox`/`drawtext`로만 그린다 — 이미징 라이브러리 의존성 없음
- 필터 그래프는 **파일로 전달**(`-filter_script:v`). 마커 수백 개면 Windows 명령줄 8191자 제한을 넘는다
- 프레임을 인덱스로 select 한다(시크 없음). 10분 세그먼트 스캔이 느린 대신 프레임 번호가 정확하다 — 이 도구의 존재 이유가 그것이다
- 창이 세그먼트를 걸치면 거부하고 쓸 수 있는 시작 지점을 알려준다

## A5 — 용량 산정치 갱신

| 항목 | 명세 §2.1 | 실측 (2026-09-15) |
| --- | --- | --- |
| 인코더 | libx264 CRF 23 | **h264_nvenc `-cq 23`** |
| 시간당 | 1.3 GB/h | **1.71 GB/h** (+32%) |
| 30시간 | ~40 GB | **~51 GB** |

nvenc의 `-cq`는 x264 `-crf`와 품질 스케일이 다르다. A2로 캡처 영역에서 크롬이 빠지면
픽셀 수가 약 5% 줄어 소폭 감소하겠지만 큰 차이는 아니다.

**결정 필요**: `crf`를 26~28로 올려 산정치에 맞출 것인가, 51GB를 받아들일 것인가.
인식 정확도에 영향이 있으므로 M1 전에 한 번 비교해볼 것. 디스크가 여유롭다면 그냥 두는 쪽이 안전하다.

## A6 — 미해결: 가로 스트레치

`docs/01_GAME_SPEC.md` 열린 항목 1. **수집 시작 전에 반드시 답을 내야 한다.**

- LDPlayer 설정값 android 1440×2560 (0.5625) vs 게임 렌더 영역 1458×2068 (0.705)
- 레터박스가 없으므로 둘 중 하나다: LDPlayer가 가로로 25% 늘리고 있거나, 실제 android 해상도가 설정과 다르거나
- 확인: `adb connect 127.0.0.1:5555` 후 **`adb shell wm size`** 한 줄

**왜 중요한가**: 스트레치가 실재하면, APK에서 추출한 스프라이트로 합성 학습 데이터를
만드는 계획(`00_PRE_RESEARCH.md` §4.2)이 깨진다. 합성 이미지는 원본 비율인데 캡처는
늘어나 있어서 맞지 않는다. 그 계획이 라벨 비용 최대 절감 수단이므로 타협 대상이 아니다.

해결책은 둘 중 하나: LDPlayer 창을 9:16에 맞춰 스트레치를 없애거나, 합성 파이프라인에
같은 스트레치를 적용하거나. 전자가 낫다.
