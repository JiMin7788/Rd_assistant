# 03 — 데이터 수집기(Recorder) 설계 명세

- 작성일: 2026-09-15
- 대상 모듈: `src/rdom/recorder/`
- 전제 경로: **A안 (LDPlayer 9 + dxcam + Windows 전역 마우스 훅)**. 실기기 변형은 §11.
- 선행 조건: 없음. **이 모듈은 M0(게임 실측)·M1(인식)보다 먼저 만들 수 있다.** 근거는 §1.2.

---

## 1. 설계 원칙

### 1.1 Recorder는 날것(raw)만 저장한다

보정은 **전부 데이터셋 빌더(`dataset/build.py`)에서** 한다. Recorder는 절대 하지 않는다:

| 보정 | 어디서 | 이유 |
| --- | --- | --- |
| 캡처 지연 오프셋 | 빌더 | 오프셋 추정치가 나중에 바뀌면 재수집해야 함 |
| 인간 반응지연 (N프레임 과거 할당) | 빌더 | 학습 하이퍼파라미터. 여러 값으로 실험해야 함 |
| 액션:비액션 리샘플링 (24.92:1) | 빌더 | 학습 설정 |
| 셀 인덱스 변환 | 빌더 | **§1.2 참조 — 가장 중요** |
| 에피소드 분할 | 빌더 (OCR) + 수집 시 힌트 | M1 인식기가 나와야 자동화 가능 |

Recorder가 저장하는 건 **프레임, 정규화 좌표, 단조 타임스탬프** 세 가지뿐이다. 이 셋은 어떤 가설이 바뀌어도 변하지 않는다.

### 1.2 셀 그리드를 몰라도 동작해야 한다

RD2의 보드 그리드는 아직 실측 전이다(전작 5×3인지, 3D 리뉴얼로 원근 왜곡이 있는지 미확인). 그런데 **수집을 그것 때문에 미룰 이유가 없다.**

Recorder는 클릭을 **클라이언트 영역 기준 정규화 좌표 `(u, v) ∈ [0,1]²`** 로만 저장한다. 그리드 정의가 나중에 어떻게 결정되든, 원근 보정 호모그래피가 필요해지든, `(u,v) → cell_index` 변환은 빌더에서 재실행하면 된다.

> **이 결정 하나가 "M0가 끝나야 M4를 시작할 수 있다"는 의존성을 끊는다.** 그리드가 틀렸다는 걸 나중에 알아도 수집 데이터는 살아남는다.

### 1.3 조용한 손상보다 시끄러운 중단

창이 움직였는데 모르고 계속 녹화하면 그 세션 전체가 쓰레기가 된다. **환경 불변식(§7)이 깨지면 즉시 녹화를 중단하고 에러를 낸다.** 복구를 시도하지 않는다.

## 2. 저장 포맷 — 프레임을 개별 이미지로 저장하지 않는다

### 2.1 용량 산정 (30시간 기준)

30 fps × 3,600 s × 30 h = **3.24 M 프레임**

| 방식 | 프레임당 | 30시간 총량 | 판정 |
| --- | --- | --- | --- |
| PNG 개별 저장 (1280×720) | ~600 KB | **1.9 TB** | ❌ |
| JPEG q85 개별 저장 | ~100 KB | **324 GB** | ❌ 파일 324만 개 = 파일시스템이 먼저 죽음 |
| **H.264 MP4 CRF 23 (1280×720)** | ~12 KB 등가 | **~40 GB** | ✅ |
| H.264 CRF 28 (960×540) | ~5 KB 등가 | ~16 GB | 인식 정확도 손실 위험 |

**결정: 세그먼트 MP4 + 별도 프레임 인덱스.** 개별 이미지 저장은 어떤 상황에서도 하지 않는다.

### 2.2 프레임 인덱스 ↔ 타임스탬프 분리 (핵심 설계)

MP4의 PTS를 신뢰하면 안 된다. 인코더가 프레임을 드롭하거나 VFR로 저장하면 인덱스가 밀리고, 그러면 **모든 액션 라벨이 조용히 어긋난다.** 이게 이 프로젝트에서 가장 찾기 어려운 버그가 될 것이다.

그래서 인코더에 넣은 프레임을 **넣는 순간 별도 파일에 한 줄씩 기록**한다:

```
frames.jsonl   ← 인코더에 써넣은 프레임 1개 = 1줄. 순서 = MP4 디코딩 순서와 1:1
events.jsonl   ← 입력 이벤트. frame_idx 없이 t_mono만 가짐
```

빌더는 `events.jsonl`의 `t_mono`를 `frames.jsonl`에 **이진 탐색**해 프레임 인덱스를 얻는다. 인코더가 뭘 하든 무관해진다.

- CFR(고정 프레임레이트)로 인코딩하고, 디코딩 프레임 수 == `frames.jsonl` 줄 수를 **세션 종료 시 검증**한다. 불일치 시 세션을 `CORRUPT`로 마킹.

### 2.3 디렉터리 구조

```
data/sessions/2026-09-20_2130_a3f1/
├─ session.json          # 환경 지문 + 캘리브레이션 결과 (§7)
├─ frames.jsonl          # 프레임당 1줄
├─ events.jsonl          # 입력·핫키·시스템 이벤트
├─ video/
│  ├─ seg_00000.mp4      # 10분 세그먼트
│  ├─ seg_00001.mp4
│  └─ ...
└─ calib/
   ├─ flash_test.json    # 지연 측정 원본 20회분
   └─ first_frame.png    # 육안 검증용 첫 프레임 1장
```

세그먼트를 10분으로 자르는 이유: 크래시 시 손실 상한, 그리고 후처리 시 병렬 디코딩.

## 3. 데이터 스키마

### 3.1 `frames.jsonl`

```jsonc
{"i": 0, "seg": 0, "si": 0, "t": 12.340815, "dup": false}
```

| 필드 | 타입 | 설명 |
| --- | --- | --- |
| `i` | int | 세션 전역 프레임 인덱스 (0부터 연속, 빈칸 없음) |
| `seg` | int | 세그먼트 번호 |
| `si` | int | 세그먼트 내 프레임 인덱스 (MP4 디코딩 시 이 값으로 seek) |
| `t` | float | `time.perf_counter()` 값. **캡처 직후 즉시 찍음** |
| `dup` | bool | dxcam이 새 프레임을 못 줘서 직전 프레임을 복제한 경우 true. 빌더가 학습에서 제외 |

> `t`는 **grab() 반환 직후**에 찍는다. 인코더 큐에 넣은 시각이 아니다.

### 3.2 `events.jsonl`

모든 이벤트는 `{"t": float, "ev": str, ...}` 형태.

**입력 이벤트** — 원시 마우스 이벤트를 그대로 남기고, 해석된 액션도 같이 남긴다.

```jsonc
// 원시 (감사·재분석용)
{"t": 45.201, "ev": "mouse_down", "btn": "left", "sx": 812, "sy": 553, "u": 0.4325, "v": 0.6144}
{"t": 45.219, "ev": "mouse_move", "sx": 830, "sy": 551, "u": 0.4520, "v": 0.6122}
{"t": 45.288, "ev": "mouse_up",   "btn": "left", "sx": 964, "sy": 549, "u": 0.5931, "v": 0.6100}

// 해석된 액션 (mouse_up 직후 생성)
{"t": 45.201, "ev": "action", "kind": "drag", "t_end": 45.288, "dur_ms": 87,
 "from": {"u": 0.4325, "v": 0.6144}, "to": {"u": 0.5931, "v": 0.6100},
 "path_n": 4, "dist_n": 0.1607}

{"t": 51.004, "ev": "action", "kind": "tap", "t_end": 51.093, "dur_ms": 89,
 "at": {"u": 0.2100, "v": 0.8312}}
```

- `action.t`는 **`mouse_down` 시각**이다 (`mouse_up`이 아니다). 사람이 의사결정을 내린 시점에 더 가깝다.
- 원시 이벤트를 남기는 이유: tap/drag 분류 임계값(§4.2)을 나중에 바꿔 재해석할 수 있어야 한다.
- `mouse_move`는 **버튼이 눌린 동안에만** 기록한다. 그냥 마우스 움직임은 버리지 않으면 초당 수백 줄이 쌓인다.

**제어 이벤트**

```jsonc
{"t": 30.000, "ev": "episode_begin", "n": 3}          // F9
{"t": 402.51, "ev": "episode_end",   "n": 3, "note": "wave 42 clear"}
{"t": 402.60, "ev": "episode_discard","n": 3, "why": "misclick"}  // F10
{"t": 410.00, "ev": "pause"}                            // F11
{"t": 455.00, "ev": "resume"}
```

**시스템 경고 이벤트** — 빌더가 해당 구간을 버릴 수 있게 한다.

```jsonc
{"t": 120.5, "ev": "warn", "code": "queue_stall", "ms": 340}
{"t": 300.1, "ev": "warn", "code": "fps_drop", "fps": 18.2}
{"t": 500.0, "ev": "fatal", "code": "window_moved", "old": [100,100,1700,1000], "new": [104,100,1704,1000]}
```

## 4. 입력 캡처

### 4.1 왜 `adb getevent`가 아닌가

에뮬레이터에서 마우스로 플레이하면, 에뮬이 마우스를 내부에서 터치로 변환한다. 이 변환이 `/dev/input`에 올라오는지는 제품·버전마다 다르고 보장되지 않는다. 게다가 ADB 왕복이 타임스탬프 정밀도를 갉아먹는다.

**Windows 전역 훅이 정답이다.** 같은 프로세스에서 `perf_counter()`를 공유하므로 캡처 스레드와의 시계 오차가 0이다.

### 4.2 tap / drag 분류

`mouse_down` → (`mouse_move`*) → `mouse_up` 시퀀스를 하나의 액션으로 묶는다.

```python
dist_n = hypot(u_up - u_down, v_up - v_down)     # 정규화 거리
dur_ms = (t_up - t_down) * 1000

kind = "tap" if dist_n < TAP_RADIUS_N else "drag"
```

- `TAP_RADIUS_N` 기본값 **0.012** (1600px 폭 기준 약 19px). 정규화 값으로 두는 이유는 해상도를 바꿔도 의미가 유지되기 때문.
- **지속시간은 분류에 쓰지 않는다.** 롱탭이 게임 내 별도 액션일 수 있어서, `dur_ms`는 저장만 하고 판단은 빌더에 맡긴다.
- 임계값은 `session.json`에 기록하지 않는다 — 원시 이벤트가 남아 있으므로 언제든 재분류 가능.

### 4.3 버려야 할 클릭

| 조건 | 처리 |
| --- | --- |
| 클라이언트 영역 밖 | `action` 생성 안 함. 원시 이벤트도 기록 안 함 |
| 에뮬 사이드바 영역 (우측 40px 등) | 동일 |
| `pause` 상태 | 동일 |
| 우클릭 / 휠 | 원시만 기록, `action` 생성 안 함 |

### 4.4 콜백은 O(1)이어야 한다

pynput 훅 콜백 안에서 좌표 변환·JSON 직렬화·디스크 쓰기를 하면 훅이 밀리고 Windows가 훅을 떼어낸다. **콜백은 `(t, raw_tuple)`을 큐에 넣고 즉시 리턴**한다. 변환과 쓰기는 별도 스레드.

## 5. 스레딩 모델

```
[T1 Capture]  dxcam.grab(region) 루프 @ target_fps
                └─ t=perf_counter() 찍고 (i, t, frame) → frame_q (maxsize=120)

[T2 Encoder]  frame_q.get() → ffmpeg stdin.write(bgr_bytes)
                └─ frames.jsonl 한 줄 append

[T3 Hook]     pynput Listener 콜백 → (t, raw) → event_q  (O(1), 즉시 리턴)

[T4 EventProc] event_q.get() → 좌표 변환 → tap/drag 판정 → events.jsonl append

[Main]        핫키 처리, 워치독(§7), 상태 출력, 종료 시 검증(§8)
```

**큐 정책**

- `frame_q`가 가득 차면 → **블로킹하지 않고** 현재 프레임을 버리고 `warn:queue_stall` 이벤트를 남긴다. 블로킹하면 캡처 주기가 밀려 `t`의 의미가 깨진다. 버린 프레임은 `frames.jsonl`에 아예 안 들어가므로 인덱스 연속성은 유지된다.
  - 단, 이 경우 `i`는 "인코더에 들어간 프레임" 기준으로 계속 증가한다. 실제 시간 간격은 `t`가 말해주므로 문제없다.
- `event_q`는 **절대 버리지 않는다.** 이벤트는 초당 수십 개라 큐가 찰 일이 없고, 액션 하나를 잃는 게 프레임 하나를 잃는 것보다 훨씬 비싸다.

**인코더 파이프 대역폭**: 1280×720 BGR 3바이트 × 30fps = **83 MB/s**. 로컬 파이프에서 여유 있다. BGRA(4바이트, 110MB/s)로 넘기지 말고 캡처 직후 BGR로 줄인다.

**코덱**: `h264_nvenc` 우선, 실패 시 `libx264 -preset ultrafast -tune zerolatency`로 폴백. NVENC를 쓰는 이유는 게임이 같은 GPU를 쓰더라도 인코더 블록이 별도라 CPU·셰이더 경합이 거의 없기 때문.

## 6. 캘리브레이션 — 캡처 지연 측정

### 6.1 측정 대상

`클릭한 시각` 과 `그 클릭의 결과가 프레임에 나타나는 시각` 사이의 지연. 여기에는 세 가지가 섞여 있다: 에뮬 입력 처리 + 게임 렌더 + dxcam 캡처. **분리할 필요 없다. 합계만 알면 된다.**

### 6.2 절차 (`calib/flash.py`, 세션 시작 전 자동 실행)

1. 게임 내 **즉시 시각 피드백이 있는 버튼**을 지정한다 (설정 메뉴 토글 등, 게임 상태를 안 바꾸는 것). 좌표는 config에 1회 기록.
2. 해당 버튼 주변 작은 ROI(예: 80×80)를 지정.
3. 20회 반복:
   - ROI 기준 프레임 저장 → 클릭 실행, `t_click` 기록 → 이후 프레임들에서 ROI 평균 절대차가 임계값 초과하는 첫 프레임의 `t_frame` 탐색
   - `offset_i = t_frame − t_click`
4. `capture_offset_ms = median(offset_i)`, `offset_sigma_ms = stdev(offset_i)`
5. 원본 20개를 `calib/flash_test.json`에 저장.

### 6.3 합격 기준

| 항목 | 기준 | 불합격 시 |
| --- | --- | --- |
| `offset_sigma_ms` | **< 15 ms** | 수집 중단. 백그라운드 프로세스 정리, 에뮬 FPS 설정 확인 |
| `capture_offset_ms` | < 120 ms | 초과 시 에뮬 렌더 설정(수직동기 등) 점검 |

> σ가 크면 오프셋 보정 자체가 무의미해진다. 이건 "나중에 고치자"가 아니라 **수집을 시작하면 안 되는 신호**다.

### 6.4 재측정 시점

세션마다 1회. 그리고 `env_fingerprint`가 바뀌면 무조건 재측정.

## 7. 환경 불변식 워치독

**5초마다** 다음을 확인한다. 하나라도 어긋나면 `fatal` 이벤트를 쓰고 **즉시 정상 종료 절차**로 들어간다 (지금까지 데이터는 살린다).

| 불변식 | 확인 방법 |
| --- | --- |
| 창 클라이언트 rect 불변 | `GetClientRect` + `ClientToScreen` 비교 |
| 창이 최소화/가림 없음 | `IsIconic`, 전경 여부 |
| Windows DPI 배율 불변 | `GetDpiForWindow` |
| 모니터 변경 없음 | `MonitorFromWindow` |
| 실효 FPS | 최근 150프레임의 `t` 간격 → 목표의 80% 미만이면 `warn` |
| 디스크 여유 | 남은 시간 × 예상 비트레이트보다 적으면 `warn`, 5분치 미만이면 종료 |

**시작 전 프리플라이트**도 같은 항목을 검사하고, 추가로:

- DPI 인식 선언: `SetProcessDpiAwarenessContext(PER_MONITOR_AWARE_V2)` — **이걸 빼면 배율 125%에서 좌표가 통째로 어긋난다**
- Windows 디스플레이 배율이 100%인지 (아니면 경고하고 진행 여부 확인)
- 예상 용량 = `시간 × 비트레이트 × 1.3` 이 디스크에 들어가는지

---

## 8. 종료 시 자가 검증

세션 종료 시 자동 실행. 실패하면 `session.json`의 `result.status`를 `CORRUPT`로 쓴다.

| 검증 | 기준 |
| --- | --- |
| 디코딩 프레임 수 == `frames.jsonl` 줄 수 | 세그먼트별 정확히 일치 |
| `i`가 0부터 연속 | 빈칸 없음 |
| `t`가 단조증가 | 위반 0건 |
| `dup` 비율 | **< 2%** (초과 시 캡처가 목표 FPS를 못 따라간 것) |
| 모든 세그먼트 MP4 열림 | ffprobe 성공 |
| `action` 이벤트 수 > 0 | 0이면 훅이 안 붙은 것 |
| 고아 이벤트 | `mouse_down` 후 `mouse_up` 없는 건이 전체의 <1% |

## 9. 육안 검증 도구 (`tools/replay_overlay.py`)

**이 도구 없이는 동기화가 맞는지 영원히 알 수 없다.** 수집기와 같은 우선순위로 만든다.

기능: 세션을 받아 임의 구간 20초를 MP4로 렌더한다.
- 액션 시각의 프레임에 **클릭 위치 원**을 그린다 (tap=원, drag=화살표)
- 오프셋 보정 전/후를 **다른 색으로 동시에** 표시
- 좌상단에 `frame_idx`, `t`, `dup` 표시

검증 기준: **사람이 20초 샘플 3개를 보고, 원이 실제로 눌린 UI 위에 찍히는지 확인.** 보정 후 원이 대상 위에 있고 보정 전 원이 살짝 뒤처져 보이면 정상이다.

## 10. 구현 순서와 검증 기준

| # | 산출물 | 검증 |
| --- | --- | --- |
| R1 | `window.py` — 창 탐색, client rect, DPI 인식, 좌표 변환 | 창을 옮겨가며 10회 측정, `(u,v)` 재현 오차 < 0.002 |
| R2 | `capture.py` — dxcam 래퍼, region 캡처, `frames.jsonl` | 60초 녹화에서 `dup` < 2%, 실효 FPS ≥ 29.5 |
| R3 | `encoder.py` — ffmpeg 파이프, 세그먼트 분할 | 프레임 수 일치 검증 통과. NVENC 실패 시 폴백 동작 |
| R4 | `hook.py` — pynput 훅, 큐 투입 | 100회 클릭 전수 기록. 콜백 소요 < 0.5ms |
| R5 | `events.py` — 좌표 변환, tap/drag 분류, `events.jsonl` | 의도적으로 탭 50 + 드래그 50 → 분류 정확도 100% |
| R6 | `calib/flash.py` — 지연 측정 | σ < 15ms 달성 |
| R7 | `watchdog.py` + 프리플라이트 | 녹화 중 창을 일부러 옮겨 `fatal` 발생 및 정상 종료 확인 |
| R8 | `tools/replay_overlay.py` | 20초 샘플 3개 육안 통과 |
| R9 | 30분 실주행 | 자가 검증 전 항목 통과, 용량이 산정치 ±20% 내 |

> **R8까지 끝나기 전에 장시간 수집을 시작하지 말 것.** 30시간을 모은 뒤에 동기화가 틀렸다는 걸 발견하면 전부 버려야 한다.

## 11. 실기기(scrcpy) 경로 변형

나중에 탐지 회피 때문에 실기기로 갈아탈 경우 **바뀌는 부분만**:

| 모듈 | 변경 |
| --- | --- |
| `capture.py` | dxcam → py-scrcpy-client `on_frame` 콜백. **서버 버전 2.4 핀 고정 필수** (클라이언트가 정체 상태) |
| `hook.py` | Windows 마우스 훅 → scrcpy 제어 소켓 이벤트, 또는 `adb shell getevent -lt`(커널 타임스탬프) |
| `window.py` | 창 rect → 스트림 해상도. `--max-size`로 축소되므로 좌표계 별도 관리 |
| 캘리브레이션 | 그대로. 다만 오프셋이 훨씬 큼(스트리밍 <50ms + 인코딩) → σ 기준은 동일하게 15ms 유지 |
| `frames.jsonl` / `events.jsonl` | **변경 없음** |

§1.1 원칙 덕분에 **빌더와 데이터 스키마는 손댈 필요가 없다.** 다만 §1.2 말미의 경고대로, 에뮬 데이터로 학습한 인식 모델은 실기기에서 렌더링 차이로 깨질 수 있으므로 **인식 모델은 재학습 대상**이다.

## 13. 열린 질문 (M0에서 답이 나와야 함)

- [ ] `calib.button_uv` — 게임 상태를 바꾸지 않으면서 즉시 시각 피드백이 있는 버튼이 어디인가
- [ ] 롱탭·더블탭이 게임 내 별도 액션인가 (있다면 `dur_ms` 임계값을 빌더에 추가)
- [ ] 드래그 중 경로가 의미를 갖는가, 아니면 시작·끝점만 중요한가 (후자면 `move_throttle_ms`를 크게 잡아 용량 절약)
- [ ] 협동 모드에서 팀원 보드가 화면에 같이 나오는가 (나온다면 `capture_region`을 내 보드로 더 좁혀 용량 절감)
- [ ] 게임 그래픽 프리셋별 렌더 차이 — 프리셋을 낮추면 인식이 쉬워지는지

## 14. 리스크 메모

수집 단계는 **입력 주입이 0**이다. 사람이 직접 플레이하고 화면만 녹화하므로, 앞선 위험 분석(`00_PRE_RESEARCH.md` §6.2)에서 "가장 낮음" 등급이며 사실상 화면 녹화와 동등하다. 자동화 리스크는 M3(룰기반 봇)부터 발생한다.

한 가지 기술적 유의점: 캡처 영역을 **에뮬레이터 클라이언트 영역으로 한정**한다(전체 데스크톱 캡처 금지). 용량 절감 목적이기도 하지만, 다른 창이 우연히 녹화에 섞이지 않게 하는 안전장치이기도 하다.
